Shared rooms your host can't read

Two people, one data room. Everything one writes is encrypted in their own browser, stored by a host that cannot read it, and opened by the other with their own key.

How it fits together

The site is a client. Rooms are their own parties.

One site can open any number of rooms, and none of them belongs to it.

  • The site is not the room. It serves this page and keeps each person's keys in their browser. It stores no records and decides nothing.
  • A room is its own party. It has its own DID, issues its own membership credentials, and its owner decides who joins.
  • The host stores, never reads. Records arrive already encrypted. Hosts can be swapped; the room keeps its identity.
  • Many rooms, one site. The two below come from this sample — any room DID works the same way. How a record is protected ↓

              How a record is protected

              Where encryption happens when Alice writes and Bob reads — and what every party in between can and cannot see.

              record encrypted or decrypted — only in a member's browser transport encryption (TSP or DIDComm), sealed to the recipient credential check — signed request plus a credential the room issued
              1

              Record encryption — members only

              Each record is encrypted in the writer's browser with a key derived from the room's MLS group at the current epoch, and bound to the room, record key and version. Only group members can derive that key: not the host, the mediator or this site.

              Every join or removal starts a new epoch. Someone removed can't read what's written afterwards; a newcomer reads earlier records through the epoch key chain, which only ever walks backwards.

              2

              Transport encryption — hop to recipient

              Every request travels inside TSP (or DIDComm), sealed to the party it's for — the host or the room's owner. The mediator routes it and learns only the next hop.

              This protects the request and the credential it carries in flight. The record inside was already encrypted; this is a second, independent layer.

              3

              Authorization — no member list

              Every request is signed by the member's own key and carries a credential the room itself issued, narrowed to one action (read, write or curate) for four hours.

              The host checks it against the room's DID and keeps no roster. It isn't a bearer token: it is bound to whoever signed, so nobody else can use a copy of it.
